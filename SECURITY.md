# Security policy

aimap is a network daemon that handles passwords, TLS private keys and
people's mail, so security reports are welcome and taken seriously.

## Reporting a vulnerability

Please report security problems privately by email to:

**serried_lapdogs_9r@icloud.com**

Do not open a public GitHub issue, pull request or discussion for a
security problem until it has been fixed.

A useful report includes:

- the aimap version (`aimap -V`) and the OpenBSD version and architecture
- the relevant parts of `aimap.conf` (with secrets removed)
- what an attacker can do, and from where: unauthenticated network
  client, authenticated user, local user, and so on
- steps or an IMAP transcript that reproduce the problem, or a
  proof-of-concept
- which process is affected, if you know: parent, listener, auth,
  keymgr, parser or store

## What to expect

aimap is a volunteer project with no dedicated security team, so
responses are best effort. Reports will be acknowledged, investigated,
and, when confirmed, fixed in a new release. The goal is coordinated
disclosure: the problem is made public once a fixed release is
available, and the reporter is credited unless they would rather not be.

## Supported versions

Only the most recent release is supported. Fixes are made in a new
release rather than as patches to older ones.

| Version         | Supported |
| --------------- | --------- |
| latest release  | yes       |
| anything older  | no        |

## Verifying releases

Release tarballs are published as assets on the GitHub releases page,
together with a signify(1)-signed checksum file and the public key.
Check a download before installing it:

```
signify -C -p aimap.pub -x aimap-VERSION.sig
```

The public key is also in this repository as `aimap.pub`; compare the
two before trusting either.

## Things to know

- All of aimap's code was generated by Claude, an AI model. It has
  extensive automated tests, fuzzing and static analysis, but it has not
  yet had an independent human security review.
- `keymgr`, which keeps the TLS private key out of the process that
  talks to clients, depends on unexported libtls/LibreSSL internals.
  An OpenBSD update that changes them could break it; see the README.
- The OpenBSD base system code aimap borrows from (see `CREDITS`) is
  maintained by the OpenBSD project. Problems in that code itself should
  go to OpenBSD, not here.
